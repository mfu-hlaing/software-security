OUTSIDERS / OPEN THE ENGINE ROOM

Small footprint.
Explicit boundaries.

Terraform defines the AWS network and hosts. Compose defines the learning services and fixed relays. A restricted host service creates one disposable target for each active learner.

Follow a request from your laptop.

1

WireGuard edge

One t3.micro, one public IPv4, UDP 51820. Private DNS and per-peer rules send each device only to its assigned team host. No public TCP entrance to the labs.

2

Team gateway

Two private t3.small hosts, 2 GiB each. Caddy serves HTTPS on port 8443 using a private CA. Personal hostnames enforce the assigned VPN source address.

3

Fixed relay

Each personal target has its own internal network and fixed upstream relay. The gateway can reach relays without joining a vulnerable target network.

4

Personal target

One of 11 target types. Non-root, read-only root, no Linux capabilities or published ports. Temporary writes disappear when the target stops.

Learning and identity

The existing learning database and uploads remain on their protected volume. Student practice accounts use a separate SQLite database. Passwords are salted and hashed; the session must also match the account’s assigned VPN address. Teacher credentials and graded submissions use the established routes.

Two narrow host services

The trusted application calls an authenticated host endpoint for a fixed set of start, stop, status and guide requests. Students cannot supply container images, commands, mounts or network settings. The AI path uses a fixed DeepSeek endpoint and supplies no model tools.

Only the learning container may connect to that host endpoint. Target and relay networks remain blocked from host sockets, metadata and off-network destinations.

What this isolation does and does not establish

Private networks, capability limits and gateway checks constrain the planted application flaws. Containers still share their team host’s kernel. This is a five-learner teaching pilot, not a kernel-exploitation service or a promise of perfect hostile-code containment. Native fuzzing and unrestricted tooling stay in each learner’s local toolbox or VM.

COMPUTE THE TRADEOFF

Five learners, five active copies.

The roster is split across two team hosts: three slots and two slots. Each learner starts one target at a time. Targets expire 60 minutes after launch; static explanations and models do not allocate a target.

Three-slot host

512 MiB learning + 128 MiB gateway + 48 MiB learning relay + 160 MiB broker limit + 3 × (160 MiB target + 32 MiB relay) = 1424 MiB of ceilings.

1424 of 1906 MiB

The observed host exposes about 1906 MiB. Roughly 482 MiB remains outside those service ceilings for the OS and Docker. Ceilings are not measured concurrency guarantees.

Two-slot host

The same fixed services plus two target/relay pairs gives 1232 MiB of ceilings, leaving roughly 674 MiB outside those limits.

1232 of 1906 MiB

CPU credits use standard mode. Sustained heavy work can throttle; local fuzzing avoids turning that into classroom-wide latency.

A WALKTHROUGH FOR YOUR LECTURER

Show the claim and the evidence.

  1. Open a learning room. Explain a trust boundary using the visual sequence, then switch to explanation slides.
  2. Sign in as a student and start a personal API target. Show the healthy baseline before changing an input.
  3. Compare a second student’s independent state. An unauthorized request to the first student’s hostname must be denied.
  4. Stop the vulnerable target and start its defended counterpart. Show both expected denial and legitimate access.
  5. Ask Scout to explain the mechanism, follow a citation, and point out the toy identity limitation.
  6. Open this architecture page, compute the monthly cost, and show the IaC, isolation tests and rollback record from the operator guide.

Use ungraded practice examples for the demonstration. Keep passwords, API keys, VPN private keys and real submissions out of screenshots.
