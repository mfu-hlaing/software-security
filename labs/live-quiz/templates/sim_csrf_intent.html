CSRF is a failure to prove request intent

A POST is not automatically CSRF. Change where the request begins, whether a victim session exists, the cookie’s SameSite setting, and the server’s token check. The model follows the request from browser to server and separately asks whether attacker code can read the response.

Correct diagnosis

Transfer the rule, not the demo

  • True CSRF: attacker-controlled cross-origin content makes the victim’s browser attach ambient authority, and the target accepts a state change without adequate intent proof. Reading the response is not required.
  • Unauthenticated POST: the endpoint may still receive bytes, but no victim authority is attached. That can be spam or abuse; it is not a successful cross-site request forgery against a victim session.
  • XSS: attacker code already runs in the target origin. It can normally issue same-origin requests, read responses, and obtain a token rendered into the page. CSRF defenses do not repair XSS; an HttpOnly cookie prevents direct cookie reading, not ambient cookie sending.
  • Defense in depth: validate a per-session token or trusted request origin, use an explicit SameSite cookie policy, keep unsafe actions off GET, and still fix every XSS sink.

This focused model uses an HTTPS POST, explicit SameSite values, a host that requires authentication, and standard same-origin policy without permissive CORS. It intentionally omits legacy default-cookie grace periods, redirects, service workers, and browser extensions.
